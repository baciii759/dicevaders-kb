# Agent 开发技术选型

本方案面向在 Windows + NVIDIA GPU 上开发 Dicevaders 自动操作 Agent 的开发者。核心方案是 **Python 单进程状态机 + 经典视觉识别 + 规则约束的局部搜索**，本地语言模型作为可关闭的策略辅助层。

设计日期：2026-11-16。代码与数据基线：[`e8c8b431d15276c8cef8b0a2820907dc489a3920`](https://github.com/baciii759/dicevaders-kb/tree/e8c8b431d15276c8cef8b0a2820907dc489a3920)。本文是开发方案，尚未在真实游戏、用户 GPU 或完整对局上验收。

## 1. 阅读顺序与结论

| 文档 | 用途 |
|---|---|
| 本文 | 明确现状、技术选型、备选方案和硬件路径 |
| [架构设计](architecture.md) | 定义模块、状态与动作契约、决策流程、输入执行和数据迭代 |
| [实施与验收计划](delivery-plan.md) | 按依赖拆分开发任务，给出验证数据、退出条件和评估方法 |

推荐分两次交付：先实现能够观察、决策、点击、校验和复盘的无模型版本，再通过对照评测决定是否启用 Qwen3-14B。首版不依赖模型下载、训练平台或向量数据库。

具体决策如下：

1. Windows 原生进程负责游戏窗口、截图、识别、局部搜索和绝对坐标点击。
2. 优先复用 380 张模板和结构化知识库，补齐视觉模块的缺口。
3. 只对已验证规则给出精确预测；随机效果和未覆盖机制必须显式标记。
4. 模型只在代码生成的候选集合中建议动作，不生成鼠标坐标，不实现计分规则。
5. 本地模型默认使用 llama.cpp 的 CUDA 后端；vLLM 用于后续 Linux/WSL2 推理或批量评测。
6. 每次更新策略、规则或模型都经过固定评测集；单局进行中固定版本。

## 2. 目标、范围与约束

沿用 [10 号文档](../../10_自动化Agent技术选型.md) 的目标：在保持通关能力的前提下，尽量减少游戏内回合数，优先争取一回合击败目标。操作次数、延迟和资源消耗是次级指标，不能通过提前失败来降低平均回合数。

| 项目 | 本次设计采用的边界 |
|---|---|
| 运行设备 | 用户已确定 Windows + NVIDIA GPU；型号、显存和系统内存待实测登记 |
| 交互方式 | 截图读取可见状态，鼠标点选执行；只有确认必须拖放的操作才走拖放适配器 |
| 游戏版本 | 数据文件声明 build `25892943`；不等同于用户当前安装版本 |
| 决策范围 | 当前可观察状态上的有限候选搜索，必要时增加短前瞻 |
| 首版范围 | 单窗口、固定分辨率与缩放配置、一个通过验收的章节/指挥官组合、受支持的规则集合 |
| 首版外 | 全部章节、无尽模式、任意分辨率、多窗口并行、在线自动训练和自动改写程序 |
| 不可观察信息 | 未显示的随机数状态、隐藏效果及精确内部数值保持未知；不从知识库名称推断当前实例状态 |

章节和指挥官的具体首测组合在采集阶段确认。可以先测舰长与第 1 章，但开始自动对局前，必须确认沿途 Boss、初始专长和可能触发的效果均已覆盖。中途出现未知效果时暂停或进入人工接管，不能把「首版」等同于已能通关第 1 章。

## 3. 仓库现状核对

以下结论来自基线提交的文件读取和数据统计，不代表真实截图识别准确率。

| 资产或模块 | 已有内容 | 开发前需要补齐 |
|---|---|---|
| [`dicevaders_data.json`](../../dicevaders_data.json) | 84 个单位、280 个混合类别条目、17 个法术、16 个 Boss、10 名指挥官 | 是描述性数据；缺少可直接执行的完整效果函数、事件顺序和状态转移 |
| [`vision/assets/manifest.json`](../../vision/assets/manifest.json) | 380 个条目，对应 380 张 PNG | 按实际 UI 区域验证缩放、遮挡、动画、重复实例与相似图标 |
| [`vision/matcher.py`](../../vision/matcher.py) | NumPy FFT 模板匹配、透明区域掩码、多尺度查找 | `_match_scales` 每模板仅取一个最佳位置；`match_category` 默认最多返回 20 个命中，不能据此还原所有单位 |
| [`vision/state.py`](../../vision/state.py) | 图标分类和按横坐标归列 | `resources`、`target`、`dice` 留空；`row` 未赋值；`kb` 参数未实际使用；默认列范围覆盖整张图 |
| [`vision/ocr.py`](../../vision/ocr.py) | 可注入 reader，提供简单整数/小数提取 | 读取首个数字片段，不能正确解释 `1.2e30`、百分比或缩写数量，也没有置信度和 ROI 来源 |
| [`vision/capture.py`](../../vision/capture.py) | 平台截图入口，Windows 使用 `ImageGrab` | 没有目标窗口绑定、DPI 映射、前台检查和帧稳定判断 |
| 规则、决策与执行 | 07、09、10 号文档有概念说明 | 尚无动作枚举器、规则模拟器、输入执行器和任务状态机 |
| 日志、评估与训练 | 10、11 号文档有草案 | 尚无轨迹采集器、标注截图集、独立测试集或端到端评估脚本 |

模板数量按 `manifest.items[].category` 统计为：84 个单位、151 个神器、64 个专长、2 个特殊图标、20 个 Boss 技能、17 个法术、10 个指挥官、16 个 Boss 和 16 个关键词图标。

### 3.1 必须修正的既有假设

| 既有表述 | 本方案的处理 |
|---|---|
| 视觉已经完成、可以确定性解析整个棋盘 | 将现有模块视为图标识别原型。数值、重复实例、阶段和商店识别通过验收后才能接执行器 |
| 列力量求和乘倍率即可准确模拟任意局面 | 基础公式只是结算的一部分。Repeat、Shock、随机得分、死亡、生成、升级和连锁触发需要独立规则 |
| 每步贪心必然得到局部最优 | 仅在候选集完整、状态准确且评价模型覆盖全部相关效果时成立；剪枝或估算时只能称为启发式选择 |
| 挪移每颗骰每回合一次 | 数据中的 `rules.Budge_Desc` 写明「每次掷骰一次」；以 `roll_id` 和裂纹状态建模，重掷后的具体重置行为仍需验证 |
| 相等分数一定达标 | `ScorePanel_Desc` 的英文、中文和社区解释存在边界差异。相等与舍入用例列入实测，最终以游戏结果为准 |
| 缺少结果变化就重复点击 | 点击可能已经生效。购买、重掷、牺牲、冻结切换等动作必须先判定结果，不能盲目重试 |
| 所有失败样本应删除 | 分离观察错误、输入失败、规则错误和策略失败；保留策略失败作评估或偏好样本 |
| Agent 版本互相对战 | 这是单人游戏。使用相同初始条件/种子集合做版本对照，不能用「互相对战胜率」作为指标 |
| 14B、24 GB、固定吞吐量就能保证运行或训练 | 引擎、量化方式、上下文、KV cache、游戏占用和训练配置都会影响内存；必须以目标设备实测决定 |

09–11 号文档保留为早期讨论。开发顺序、架构边界、模型部署和验收标准以本目录为准。

## 4. 技术选型表

| 层 | 默认选择 | 选择依据 | 备选与启用条件 |
|---|---|---|---|
| 语言与依赖 | Python 3.11、uv、锁文件 | 直接复用现有 Python 模块；统一可复现环境 | 解释器升级另跑兼容性测试；推理和训练环境单独锁定 |
| 编排 | 显式有限状态机、类型化函数、单动作串行 | 一局只有一个输入目标，容易复盘、取消和处理部分完成 | 工作流变成多任务持久调度后再评估框架；首版不引入 LangGraph、多 Agent 协作或分布式队列 |
| 数据契约 | Pydantic v2，严格校验，禁止未知字段 | 明确区分空值、未观测、无效枚举和非法参数 | 生成 JSON Schema 给推理服务；业务合法性仍由规则层校验 [S1] |
| 截图 | `mss` + Win32 窗口信息 | 可截取区域，便于复用内存帧 [S2] | `ImageGrab` 留作诊断回退；只有实测捕获失败或速度不足时才替换后端 |
| 图标与棋盘 | OpenCV `matchTemplate` + ROI + 多命中抑制 | 复用现有模板，支持逐格分类和定位 [S3] | NumPy 版作为对照；积累标注后仍无法处理变形/遮挡，再考虑检测模型 |
| 数字与文字 | Tesseract + `pytesseract`，按 ROI 预处理与字段语法解析 | 当前已有 OCR 接口，先完成数字、符号和置信度接入 [S4] | 视觉模型仅补读低置信度裁剪，输出继续接受约束校验 |
| 知识查询 | 按 `kind/key` 的内存索引，规则关系表 | 数百条记录可直接查询；精确内部键优先 | 经验量增大后加 SQLite 索引；模糊文本检索确有收益再加全文/向量搜索 |
| 规则与数值 | Python 效果函数、显式事件队列、`int`/`Decimal` | 可测试、可追踪顺序、可报告未支持效果 | 复杂局面不强行计算精确分数；无尽模式另设计大数语义 |
| 决策 | 合法动作枚举 + 确定性启发式 + 小规模期望搜索 | 适合离散动作与局部决策，模型离线时仍能工作 | 相同预算下，短 beam 搜索有可测收益才开启 |
| 输入 | `pydirectinput`，封装绝对坐标左右键点击 | 保留仓库的点阵点击方向，基于 Windows 输入接口 [S5] | 多屏、DPI 或输入兼容测试失败时，用 Win32 `SendInput` 适配器补齐 [S6] |
| 本地模型 | Qwen3-14B 候选，llama.cpp CUDA 推理服务 | 延续仓库 14B 方向；文本决策可独立验证 [S7][S8] | 资源受限选 Qwen3-8B；模型不能改善任务指标时保持关闭 |
| 模型调用 | HTTP 适配器 + 超时 + 简化 JSON Schema | 屏蔽引擎参数差异，模型服务故障不阻塞主循环 | vLLM 用于 Linux/WSL2 的批量评测或独立推理 [S9] |
| 轨迹与分析 | JSONL + PNG；SQLite 索引 | 逐事件保存证据，索引可从原始事件重建 | 数据较大时导出 Parquet/批量分析，不提前部署数据库服务 |
| 验证 | pytest；规则不变量使用 Hypothesis；固定截图与轨迹集 | 区分感知、规则、执行和策略问题 | 游戏对局单独验收，单元测试不能代替通关测试 |
| 后续训练 | 独立 Linux 环境，LLaMA-Factory + QLoRA SFT 候选 | 先复用已清洗轨迹，再评估模型收益 [S10] | 可比较偏好数据充分时评估 DPO；环境能可靠重置且模拟器通过验证后再考虑 GRPO |

OpenCV 替换不能只改一个函数后沿用旧阈值。应验证透明掩码、缩放与相似度含义，重新校准阈值。首个实现可对已校准网格逐格分类；全局按钮定位则保留多个局部峰值，再做重叠抑制。

## 5. 模型与硬件决策

### 5.1 模型职责与候选

| 方案 | 定位 | 采用条件 |
|---|---|---|
| 无模型规则基线 | 首版必交付 | 受支持动作能闭合执行，提供后续对比基线 |
| Qwen3-14B | 首选待测文本策略模型 | 相同状态、候选集合和规则版本下，能改善商店选择或 Boss 准备策略，且延迟/显存达标 |
| Qwen3-8B | 低资源对照组 | 14B 与游戏争抢显存，或 8B 质量足够接近且更省资源 [S11] |
| Qwen3.5-27B 等新模型 | 后续对照候选 | 新模型要通过相同任务集。官方已有开放权重，不能沿用旧文档对整个 Qwen3.5 家族的笼统判断 [S12] |
| 视觉语言模型 | 辅助识别候选 | OCR 在明确的难例集上不达标，且裁剪识别能改善准确率；不直接取得点击权限 |

Qwen3-14B 的官方模型卡说明了许可证和思考模式切换，未证明 Dicevaders 的胜率或单步时延。BFCL 排名也不能替代本项目评测。保留 14B 是为了形成可检验基线，不是宣称它是所有设备上的最优模型。

默认使用非思考模式，并记录实际 chat template 和采样参数。关闭思考的请求参数由推理后端适配器处理；先做能力探测，不能只在提示词里写「不要思考」。不照搬旧文档的低温度经验值，采样参数以模型建议和离线对照结果确定。

### 5.2 Windows 主机的部署路径

| 硬件条件 | 首轮试验建议 | 需要验证 |
|---|---|---|
| 未知型号/显存 | 先完成无模型版本；采集 GPU、驱动、游戏峰值占用 | 保证游戏本身稳定，避免先购置设备 |
| 8–12 GB 显存 | Qwen3-8B 的兼容量化文件，必要时关闭模型或 CPU 分担 | 游戏与模型同时运行后的峰值、系统内存和交互延迟 |
| 16 GB 显存 | 尝试 14B GGUF Q4_K_M，保留 8B 回退 | 能否为游戏、KV cache 和运行缓冲留出余量；这不是容量保证 |
| 24 GB 显存 | 先测 14B Q4/Q5；资源充足再比较更高精度 | 同时运行游戏的 p95 延迟、显存峰值和任务质量 |
| 48 GB 及以上/独立推理机 | 比较更高精度、其他候选和批量评测 | 只有任务指标改善才扩大模型；训练预算另算 |

以上是试验起点，不是已测配置。`14B × 4 bit ÷ 8 ≈ 7 GB` 只是理想化权重位宽下界，不能作为模型文件大小或总显存。实际还包含未量化张量、量化元数据、KV cache、计算缓冲和游戏占用。

推理服务优先使用固定版本的 llama.cpp Windows CUDA 构建和经验证的 GGUF 文件。记录模型来源、revision、文件 SHA-256、许可证、引擎版本、上下文上限和实际 GPU 卸载配置。服务仅绑定本机；后续独立推理机再增加受控网络连接。

vLLM 在本方案中属于可选的独立服务。其 NVIDIA 安装路径以 Linux 为主，Windows 可考虑 WSL2；游戏截图与输入仍保留在 Windows 原生进程 [S9]。模型服务移到 WSL2 并不会增加物理显存。

FP8 要同时区分存储格式和计算路径。vLLM 文档将原生 W8A8 与 Turing/Ampere 上的 W8A16 路径分开说明，不能把 RTX 3090 和 RTX 4090 视为相同 FP8 执行条件 [S13]。

### 5.3 训练硬件不提前承诺

先采集目标序列长度、batch、LoRA rank、优化器、检查点和量化配置，再跑小规模显存试验。24 GB 是否能训 14B、48 GB 是否足够 DPO，都需要配置和测量支撑。多卡显存只有在正确分片后才可能共同承载模型，不能直接相加推导单卡可用性。

训练时不与游戏争用同一张卡。完成离线训练、固定评测和人工抽查后，部署一个带版本号的候选；不能把「样本累计到 1000 条」或「合法率低于 95%」直接设成自动训练开关。

## 6. 关键设计取舍

| 决策 | 获得的收益 | 接受的限制 | 重新评估条件 |
|---|---|---|---|
| 模块化单体，单动作串行 | 输入有唯一所有者，容易停机与复盘 | 一次只控制一个游戏窗口 | 需要同时评测多个独立游戏实例 |
| 先规则后模型 | 可定位模型之外的故障，避免用训练掩盖识别错误 | 需要手工实现规则子集 | 规则基线完成后，模型在固定指标上有收益 |
| 精确键查询优先 | 可追踪、可复现、不依赖 embedding | 不擅长自然语言相似经验查找 | 文本经验库增长且检索评测证明需要 |
| 单步执行后重新观察 | 能发现界面漂移、部分完成和未知弹窗 | 增加截图与验证时延 | 独立验证过的短 UI 子流程可做受控组合动作 |
| 规则有覆盖等级 | 未实现效果不会被误称为精确模拟 | 未知构筑需要接管 | 新机制有真实证据、规则测试和对局验证 |
| 离线晋级策略 | 便于回滚，保留评估集独立性 | 学习结果不能立刻接管当前对局 | 不改为无验收的自动覆盖，后续只自动化验收流程 |
