# Agent 实施与验收计划

按「可观察、可校验、可执行、可比较」的顺序开发。先交付无模型版本，再决定模型和训练是否值得引入。技术选择见 [选型说明](README.md)，接口和执行语义见 [架构设计](architecture.md)。

本文列出的门槛是建议的初始验收标准，不是已经测得的结果。当前交付只有设计文档；未完成真实截图采集、Windows 输入测试、GPU 测量、Agent 实现或通关验证。

## 1. 开发里程碑

| 阶段 | 任务与产物 | 依赖 | 退出条件 |
|---|---|---|---|
| M0 运行基线 | 登记 Windows/GPU/驱动/内存/游戏 build；录制 UI 流程；采集并标注截图；形成支持范围 | 无 | 确认目标窗口、DPI、阶段转换、首测章节/指挥官和未知机制清单 |
| M1 状态识别 | Pydantic 契约、窗口/ROI 校准、重复实例识别、骰子/资源/商店解析、字段证据 | M0 | 能在固定截图集上生成完整状态；未知与空值不混淆；只读现场运行通过 |
| M2 受控执行 | 输入适配器、停止热键、前后置条件、意图日志、部分完成恢复 | M1 | 每类动作在可控状态下通过成功/失败/失焦测试；首轮使用人工逐步模式 |
| M3 规则与策略 | KB 适配器、规则覆盖表、事件计算、合法动作、规则基线、深度 1 局部搜索 | M1；联调需 M2 | 受支持规则的黄金案例和不变量通过；离线 dry-run 不产生违规候选 |
| M4 无模型试运行 | 连接主循环、运行记录、故障归因、固定范围真实对局 | M2、M3 | 在声明范围完成自动对局；所有中断和接管单独统计；通过可靠性门槛 |
| M5 可选模型 | llama.cpp CUDA 服务、候选 schema、非思考适配、8B/14B 对照 | M4 | 相同条件下有可复现的质量收益，且可靠性、延迟与资源不退化到门槛外 |
| M6 离线改进 | 经验检索、参数搜索、训练数据导出、可选 QLoRA/DPO | 可信轨迹与独立评估集 | 候选通过离线回归和真实对局验证，保留版本与回滚方法 |

M1 之后，M2 与 M3 可以分别开发，但必须使用同一契约版本联调。首版完成点是 M4；M5、M6 不阻塞首版交付。排期以 M0 采集到的 UI 复杂度和规则覆盖清单估算，不提前承诺训练或通关时间。

## 2. 可直接进入开发的任务清单

| ID | 任务 | 验证方式 |
|---|---|---|
| A01 | 固化 `Frame/Observation/GameState/Action/Event`；为动作建立判别联合类型 | 缺失值、非法枚举、额外字段、旧 schema 和大数字样例 |
| A02 | 建立 KB 适配器，保留 `kind` 和大小写，生成版本哈希 | 校验实体引用、重复键、未知类型和占位成长值 |
| A03 | 绑定游戏窗口，建立客户端像素到屏幕坐标映射 | DPI、多屏、移动窗口、最小化与失焦场景 |
| A04 | 将全图模板查找改成 ROI/逐格识别，支持重复实体 | 多个同类单位、相似模板、遮挡、空格与不可用格 |
| A05 | 接入数字、骰子状态、商店价格、阶段和按钮检测 | 带标注截图比较；指数、负数、百分比、缺失字段 |
| A06 | 建立动作意图、执行回执和验证日志，支持崩溃后识别未完成动作 | 在点击前后和目标选择中间注入进程中断 |
| A07 | 实现绝对坐标点击、逐步验证、停止与恢复 | 不依赖得分策略，单独验证每类 UI 操作 |
| A08 | 编写有限规则集合和显式事件计算，输出覆盖等级 | 游戏前后证据、确定性用例、资源/实例不变量 |
| A09 | 实现合法候选、规则基线、深度 1 搜索和随机分布接口 | 构造可枚举小状态，与穷举最优结果对比 |
| A10 | 接入阶段状态机、预算、模型关闭时运行和离线回放 | 超时、未知阶段、无候选、未知规则与日志失败 |
| A11 | 实现评测报告，分开感知/执行/规则/策略故障 | 从原始事件重算指标，与人工标注对照 |
| A12 | 实现模型适配与候选建议，再做模型收益评测 | 超时、服务离线、错 schema、过期响应和候选越界 |

首个集成迭代只覆盖「已观测普通骰子的挪移 → 校验 → 发射 → 观察结算」。接着补商店购买并放置、重掷及冻结，再覆盖沿途 Boss 和专长。没有覆盖购买触发、法术或特殊骰之前，不将这些动作交给模型填补。

## 3. 验收数据如何组织

### 3.1 截图与 UI 流程

建立初始至少 300 张人工标注的稳定截图，另收集动画、遮挡和未知弹窗作为拒绝集。数量是起点，不能代替对每种阶段、动作和关键字段的覆盖。截图按对局及采集批次切分，不能让相邻帧跨训练/测试集合。

每张标注包括游戏 build、窗口尺寸、DPI、阶段、实体实例/位置、数字原文与解析值、按钮状态。支持范围内的每个关键阶段都要有独立测试样例。

使用完整录像或连续截图确认实际操作顺序、金额扣除时机、动画结束信号和目标选择流程。静态截图无法单独证明某次点击的业务结果。

### 3.2 规则黄金案例

每个已实现规则都保存初始状态、动作、预期事件及结果，引用游戏证据和规则版本。最少覆盖以下类型：

| 场景 | 必须证明的行为 |
|---|---|
| 普通骰与空列 | 基础得分只计算实际命中的单位，空列合法与否按真实 UI/规则确认 |
| 挪移边界 | 无特殊效果时 1/6 不回绕；同次掷骰不可重复挪移；重掷后状态独立验证 |
| 特殊挪移/Boss | Torpedo、Roxy、Noel 等机制不能套普通骰规则；未实现时明确阻断 |
| 资源不足 | 货币、心心、挪移和时空点不足时不生成相应动作 |
| 得分与 Repeat | 重复结算和新的得分事件区分；不会错误触发「得分后」效果 |
| Trigger 与代价 | 触发 `▶` 后效果时，代价是否执行按机制验证；不能通用复制整段描述 |
| Shock 与负力量 | 验证跳过条件及次数；负力量得分与牺牲/吸收值分开处理 |
| 位置与生命期 | 牺牲方向、死亡重生、护盾、生成失败、棋盘满的处理有证据 |
| 动态数值 | 当前力量、神器等级/XP、百分比与倍率随事件更新，不使用静态定义代替 |
| 达标边界 | 等于防御、UI 舍入、接近阈值和多回合累计攻击不误判 |
| 随机效果 | 普通骰期望与穷举结果一致；未知概率分布不伪装成确定结果 |
| 连锁循环 | 达到事件预算后报告未完成模拟，不返回伪精确收益或无限分 |

属性测试检查：合法动作不使资源出现未经规则解释的负值；占用格无重复实例；单位消失必须有事件；相同确定性输入产生相同结果；未知字段不会隐式变成零。

### 3.3 输入与恢复故障集

| 故障 | 预期行为 |
|---|---|
| 点击没有注入或被游戏忽略 | 在证明未生效后按动作策略有限重试；保持原始证据 |
| 点击生效，后续截图超时 | 标记结果未知，先观察；不再购买、重掷或牺牲一次 |
| 商品已经扣费，停在放置态 | 恢复目标选择步骤；不重新点击商品 |
| 冻结状态切换已生效但响应延迟 | 读取状态后判断目标布尔值，不连续右键 |
| 窗口移动、DPI 改变或切到其他应用 | 使校准失效，停止提交新输入 |
| 用户手动操作 | 暂停 Agent，丢弃旧候选，恢复时重新观察 |
| 模型服务离线或迟到 | 状态可信时使用规则策略；过期响应直接丢弃 |
| 轨迹磁盘满或写入失败 | 停止发出新游戏动作，报告存储问题 |
| 发送输入后进程崩溃 | 重启读取未完成意图，核对实际状态后再继续 |
| 未知弹窗或未知规则 | 记录并暂停，不用默认坐标或通用点击绕过 |

## 4. 指标与建议门槛

指标先固定定义，再讨论数值。首次性能测量使用用户实际 GPU、游戏设置和窗口布局；在报告中记录设备信息。

| 指标 | 定义 | 初始建议门槛 |
|---|---|---|
| 关键字段准确率 | 标注集上价格、资源、骰面、目标、状态等字段完全正确的比例 | 支持范围内至少 99.5%；按字段分别报告，不能用大量易例掩盖难例 |
| 错误放行率 | 字段错误但被判定可执行的决策帧 / 所有可执行决策帧 | 初始封闭验收集为 0；同时报告样本量，不能据此宣称真实风险为零 |
| 拒绝/未知率 | 无法生成可信状态的帧 / 全部需要决策的帧 | 必须报告且不得以大量拒绝来掩盖错误放行；M4 试运行建议不超过 5% |
| 规则预测准确性 | 黄金案例的最终状态与关键事件一致性 | 所有声明为 `exact` 的案例通过；不一致就降级覆盖等级 |
| 输入正确性 | 已发出动作中，目标与实际操作语义一致的比例 | 验收集中不出现错误目标或重复副作用；建议累计至少 1000 次已验证动作 |
| 停止与恢复 | 注入故障后是否继续发出未经验证的新动作 | 故障集全部按预期暂停或恢复，无盲目重试 |
| 软件决策时延 | 稳定帧可用到动作提案通过校验，排除游戏动画 | 无模型 p95 先以 2 s 为目标；模型节点以 5 s 为目标，超时回退；均需实测 |
| 端到端时延 | 开始观察到动作结果确认 | 单独记录截图、识别、规划、模型、输入与游戏等待的 p50/p95 |
| 自动完成率 | 无接管完成并得到明确终局的局数 / 所有启动局数 | 先报告实测，不以仅统计成功完成局来美化指标 |
| 胜率与回合数 | 声明范围内所有启动局的胜率，以及胜局回合数分布 | 保持胜率不退化，再比较胜局回合数；不能用更快失败当优化 |

1000 次动作还必须覆盖各动作类型和异常路径。增加动作样本不能替代罕见高影响故障测试。准入指标之外的性能问题可以继续优化，但错误目标、重复购买、未知价格放行等问题应阻止自动运行范围扩大。

## 5. 策略与模型怎么比较

固定游戏 build、知识、规则、布局和运行模式，比较以下版本：

| 版本 | 作用 |
|---|---|
| B0：固定优先级规则策略 | 最简单的可复现对照，所有动作仍通过合法性与执行校验 |
| B1：局部搜索 | 使用同一规则集合，测量搜索是否改善游戏结果 |
| B2：短前瞻 | 以相同时间预算与 B1 对比，说明剪枝和超时次数 |
| L8/L14：模型辅助 | 只在相同候选集合中建议，测量模型的增量收益 |
| F：微调候选 | 与对应未微调模型使用相同提示、规则和预算 |

离线先比较可信状态下的候选质量、非法建议率、超时率和时延。静态状态集只能评价动作选择，不能推导通关率。多个动作同样合理时，接受集合或结果评价优于唯一答案的字符串匹配。

在线先用固定且独立的至少 30 个初始条件做试验，报告样本数、种子、章节、指挥官、胜负、回合、接管和失败类别。30 局仅作为试验起点；收益不确定时扩大样本，不直接宣称显著提升。

如果能可靠重置种子/存档，按初始条件做配对比较，并报告胜率置信区间和胜局回合分布。不同策略改变随机数消耗后，后续事件可能不同。不能重置时使用分层随机分配，并明确其证据弱于严格配对。

模型上线要求：执行和状态校验不退化；在保留胜率的前提下改善回合数、构筑选择或接管率中的预先指定指标；显存和时延不过预算。证据不充分就保留无模型策略，不因为模型更大或更新而替换。

## 6. Windows 与 GPU 验证

1. 登记 GPU 型号/显存、驱动、Windows 版本、系统内存和显示配置。
2. 只运行游戏与无模型 Agent，测截图成功率、CPU 占用和游戏显存峰值。
3. 独立启动固定版本推理服务，用同一批状态测 schema 合格率、延迟和峰值内存。
4. 同时运行游戏和模型，覆盖实际使用的上下文长度、输出上限和长时间对局。
5. 模拟模型 OOM、服务退出和请求超时，验证主循环可回退且不误点。
6. 根据任务指标选择 8B/14B、量化文件、上下文上限和 GPU 卸载配置。

测试时区分首次加载、冷请求和暖请求。报告 p50/p95、运行次数、峰值显存、游戏卡顿及模型回退次数，不只记录平均 token/s。

模型服务初始并发设为 1，先使用约 4K token 的上下文预算和短候选响应；这是可调整的试验配置。提示超长时优先裁剪无关知识和经验，不能截掉动作前置条件。所有配置随报告归档。

## 7. 训练与经验更新的准入条件

满足以下条件后再进入训练试验：

- 错误已归因为策略选择，而非识别、输入或规则实现。
- 可信轨迹覆盖主要动作和失败类型，并完成去重和来源标记。
- 训练、经验检索和测试集按对局/种子族隔离，测试集不参与调参。
- 候选标签经过真实结果、已验证模拟或人工审查；预测分不是默认真值。
- 已明确收益指标、基线、预算和失败回滚办法。

训练数据同时保留负例与失败原因。SFT 使用可信正例；DPO 使用同一状态下经过验证的偏好对。先调检索和规则参数，再判断 SFT 是否必要；DPO 和 GRPO 都不是必经阶段。

训练硬件评估至少记录序列长度、micro batch、梯度累积、量化、rank、优化器和检查点设置。先跑小样本试验，再估算成本，不能照用旧文档固定的 20 GB 或 56 GB 数字。

## 8. 交付物与待确认项

M4 交付应包含锁定依赖的可运行 Agent、支持范围配置、校准工具、停止/恢复入口、标注数据索引、规则覆盖表、离线评测、真实对局报告和已知问题。模型权重、原始录像和存档作为本地/受控外部产物管理，不直接并入文档仓库。

| 待确认项 | 确认时间 | 影响 |
|---|---|---|
| NVIDIA 型号、显存、系统内存、驱动 | M0 | 模型大小、量化、GPU 卸载和是否需要独立推理机 |
| 游戏实际 build 与语言 | M0 | 数据、模板、OCR 与规则是否可复用 |
| 固定分辨率、窗口模式、DPI | M0 | ROI、坐标和输入验收范围 |
| 首测章节、指挥官、挑战设置 | M0 | 规则白名单与通关目标 |
| 目标分判定、商店顺序、扣费时机、重掷重置规则 | M0 至 M3 | 精确规则、状态机和动作验证条件 |
| 是否有可复制的种子/存档重置方式 | M4 前 | 策略对照的强度；缺失时仍能记录对局，但不能宣称严格重放 |

开发开始时先完成 A01–A05 和一个单动作校验样例。根据这组结果确定首版规则范围，再进入完整对局；模型和训练选择保持可逆。
